# Atlas - 路过 MVP 技术方案

## 1. 文档目的

本文档用于定义“路过（Atlas）”项目的整体产品方向、一期 MVP 范围、技术架构、前后端模块划分、数据模型、接口草案与版本演进路径。文档的主要使用对象包括：

- 前端开发 Agent / 工程师
- 后端开发 Agent / 工程师
- 产品 / 策划
- 设计 / 交互
- 后续负责版本演进与内容扩展的协作成员

本文档的目标不是描述抽象愿景，而是提供一份**可直接进入研发拆解与实现**的基线方案。

---

## 2. 项目定义

### 2.1 项目名称

- 中文产品名：**路过**
- 项目代号：**Atlas**

### 2.2 项目定位

“路过”是一个**在线互动式虚拟旅行体验产品**。用户从世界地图进入区域、景点与事件层，在景点中完成轻量交互，包括：

- 打卡
- 拍照
- AI 合成
- AI 角色偶遇
- 随机事件触发
- 收藏与分享

产品强调的不是传统重度游戏玩法，而是：

- 地图层级进入感
- 场景沉浸感
- 轻交互反馈
- 风景与人物的关系构建
- 旅行过程中的“到达、停留、遇见、记录”

### 2.3 核心设计原则

1. **轻玩法，重体验**：不做复杂战斗和开放世界移动，优先强化进入感、交互感和分享感。
2. **伪开放域**：通过镜头推进、层级切换和场景转场营造探索感，而不实现真连续大世界。
3. **配置驱动**：地图、景点、动作、事件、奖励、AI 模板均通过配置驱动，避免写死。
4. **前后端解耦**：前端负责互动表现和用户体验，后端负责内容、状态、规则和异步任务。
5. **服务端主导内容更新**：新增景点、活动和事件应尽量通过配置与资源扩展完成。

## 3. 用户体验目标

### 3.1 用户主路径

用户的核心体验路径定义为：

1. 登录进入产品
2. 浏览世界地图
3. 进入一个已开放区域
4. 选择一个景点
5. 在景点中执行动作（Action）
6. 触发事件（Event）或 AI 结果
7. 获得奖励、记录与可分享内容
8. 返回上层继续探索

### 3.2 产品价值验证目标

MVP 阶段需要重点验证以下四件事：

1. 用户是否愿意从地图进入景点探索
2. 景点内轻交互是否能提供持续兴趣
3. AI 合成 / 偶遇是否构成足够强的亮点
4. 用户是否愿意收藏、保存、分享生成结果

## 4. 产品整体规划

本项目按“三层规划”推进：

### 4.1 长期规划（产品层）

长期目标是构建一个可持续扩展的虚拟旅行互动平台，支持：

- 多区域 / 多城市 / 多主题地图扩展
- 景点内容持续上新
- 节日活动与限时事件
- AI 图片、角色、旅行明信片等能力扩展
- 图鉴、成就、旅行记录等长期留存系统
- 后续嵌入 App 或形成多端产品形态

### 4.2 中期规划（系统层）

系统层目标是建立稳定的分层架构：

- 世界地图层
- 区域地图层
- 景点场景层
- 事件展示层
- 配置驱动内容层
- 用户进度层
- AI 异步服务层

中期重点不是扩更多玩法，而是保证：

- 内容可扩展
- 地图层次清晰
- 前后端协议稳定
- 新景点接入成本足够低

### 4.3 当前规划（MVP 层）

当前版本只做一个可闭环、可试玩、可演进的基础版本，确保研发与 Agent 可以快速推进。

## 5. 技术路线结论

### 5.1 首发形态

**Web First**

原因：

- 跨平台访问成本低
- 登录体系天然适配
- 服务端内容驱动更新方便
- AI 图片上传、生成、结果展示链路成熟
- 便于快速验证玩法与产品结构
- 后续可嵌入 App 或 H5 容器

### 5.2 前端技术栈

建议：

- 框架：**React / Next.js**
- 场景渲染：**PixiJS**
- 动画：**GSAP**
- 状态管理：**Zustand**
- 数据请求：**TanStack Query**
- 样式：**Tailwind CSS** 或 CSS Modules

结论：

- 不建议用纯 DOM / 页面跳转方式实现核心互动
- 不建议一期直接使用 Unity WebGL
- 不建议先做 3D
- 不建议以 GIS 地图 SDK 作为主体验层

### 5.3 后端技术栈

建议：

- 框架：**NestJS** 或 **FastAPI**
- 数据库：**PostgreSQL**
- 缓存：**Redis**
- 队列：**BullMQ**（Node）或 Celery（Python）
- 对象存储：用于原图、生成图、场景资源

### 5.4 AI 能力架构

AI 相关能力独立服务化，不与主业务逻辑强耦合。主要包括：

- 图片上传预处理
- 人像与场景合成
- AI 角色偶遇生成
- 明信片 / 海报生成
- 审核与安全控制

## 6. 系统整体架构

建议分为 6 层。

### 6.1 App Shell 层

负责标准产品能力：

- 登录
- 用户信息
- 图鉴 / 成就页
- 分享页
- 生成记录页
- 活动入口
- 设置页

### 6.2 Scene Runtime 层

负责互动场景运行：

- 世界地图场景
- 区域场景
- 景点场景
- 事件演出层

### 6.3 Camera & Transition 层

负责：

- 世界地图到区域地图的镜头推进
- 区域到景点的缩放与转场
- 景点到事件层的切换
- 返回上一级
- 焦点聚焦 / 平移 / 缩放

这是核心体验层，必须单独抽象。

### 6.4 Game Logic / Rule 层

负责轻量规则逻辑：

- 某景点是否可见 / 可进入
- 某 Action 是否可执行
- 执行后触发什么事件
- 奖励是否发放
- 是否触发 AI 异步任务

### 6.5 Content Config 层

负责所有可配置内容：

- Region
- Spot
- Action
- Event
- Reward
- AI Template

### 6.6 AI Service 层

负责异步执行和内容安全能力。

## 7. 地图层级设计

为保证扩展性，统一使用 4 层地图 / 场景抽象。

### 7.1 L1：World Map

作用：

- 展示整个世界/全国/全球的概貌
- 承担入口、世界观与未来开放预告功能

用户感知：

- 知道产品有更大的探索空间
- 知道哪些区域已开放 / 即将开放

### 7.2 L2：Region Map

作用：

- 展示一个区域/城市内部结构
- 提供景点入口
- 呈现节点与路线关系

### 7.3 L3：Spot Scene

作用：

- 展示单个景点场景
- 呈现景点内可执行动作
- 是核心互动层

### 7.4 L4：Event Layer

作用：

- 承接动作结果
- 展示随机事件、偶遇、奖励、生成结果

## 8. 核心玩法模型

### 8.1 一期玩法原则

玩法本身不复杂，但必须可扩展，因此：

- 先控制玩法数量
- 用统一抽象承载多种景点交互
- 所有内容规则配置化
- Action 先做少量高频类型

### 8.2 Action 统一抽象

所有景点内可做的事，统一定义为 `Action`。

一期先支持 4 类：

#### 1. `check_in`
- 景点打卡
- 记录到访
- 解锁图鉴
- 发放基础奖励

#### 2. `photo`
- 拍照 / 上传照片
- 选择模板
- 提交 AI 合成任务
- 获取结果图

#### 3. `encounter`
- AI 角色偶遇
- 生成角色卡、对话片段或剧情卡

#### 4. `random_event`
- 随机事件
- 根据配置和权重触发
- 返回剧情卡、奖励或隐藏线索

后续扩展可加入：

- `collect`
- `dialogue`
- `unlock`
- `mini_game`
- `share_task`

### 8.3 Event 设计原则

Event 不是独立地图层，而是 Action 的结果承载体。

Event 用于表达：

- 某次到达发生了什么
- 某个动作带来了什么反馈
- 某个景点有什么差异化体验

Event 可包含：

- 标题
- 文案
- 图片 / 动画模板
- 分支选项（可选）
- 奖励结果
- 是否一次性
- 是否受时间 / 条件影响

## 12. API 设计草案

以下接口仅作为第一版协议建议。

### 12.1 内容查询接口

#### 获取世界地图
`GET /api/world`

返回建议：

- world 基础信息
- 开放区域列表
- 区域状态
- 用户已解锁信息

#### 获取区域详情
`GET /api/regions/{regionId}`

返回建议：

- region 信息
- spot 列表
- 节点关系
- 区域进度

#### 获取景点详情
`GET /api/spots/{spotId}`

返回建议：

- 景点基础信息
- 可执行 action 列表
- 景点资源
- 当前用户状态

### 12.2 用户行为接口

#### 景点打卡
`POST /api/spots/{spotId}/check-in`

#### 获取某景点可执行动作
`GET /api/spots/{spotId}/actions`

#### 执行动作
`POST /api/actions/{actionId}/execute`

返回建议：

- action 执行结果
- 事件内容
- 奖励结果
- 是否触发 AI 任务
- 任务 ID（如有）

### 12.3 AI 任务接口

#### 上传图片
`POST /api/uploads/image`

#### 提交图片合成任务
`POST /api/ai/photo-generate`

#### 查询任务状态
`GET /api/ai/tasks/{taskId}`

#### 获取任务结果
`GET /api/ai/results/{taskId}`

### 12.4 用户资产接口

#### 获取图鉴
`GET /api/me/collections`

#### 获取生成记录
`GET /api/me/generated-assets`

#### 获取成就
`GET /api/me/achievements`

## 14. 当前版本规划（MVP）

### 14.1 MVP 目标

做出一个可以完整跑通的最小闭环版本，交付给内部测试或早期体验。

### 14.2 MVP 范围

#### 必做
1. 登录能力
2. 世界地图入口页
3. 1 个 Region
4. 5~10 个 Spot
5. 每个 Spot 至少 2~4 个 Action
6. 支持 `check_in / photo / encounter / random_event`
7. 图鉴 / 收藏基础能力
8. AI 图片生成一条完整链路
9. 分享结果页

#### 不做
1. 多人实时互动
2. 连续自由移动开放世界
3. 复杂 NPC 行为系统
4. 重剧情树
5. 大规模经济系统
6. 复杂小游戏平台
7. 完整 CMS 后台

### 14.3 MVP 成功标准

- 用户能从地图进入景点
- 用户能在景点触发至少两种互动反馈
- AI 生成链路可用
- 用户可看到奖励与记录结果
- 前后端协议稳定，可继续加内容

## 17. 开发排期建议

按照一个小团队并行推进，建议 6 周完成 MVP 基础版。

### 第 1 周：方案与协议确认
- 技术栈定稿
- 模型定稿
- 接口协议定稿
- 设计资源规范确认

### 第 2 周：前端场景骨架 / 后端配置骨架
- 前端完成地图分层骨架
- 后端完成配置读取和基础表结构

### 第 3 周：景点与 Action 骨架

## 20. 结论

“路过（Atlas）”的一期不应被定义为一个复杂游戏项目，而应被定义为：

> 一个以地图进入感、景点轻交互和 AI 内容生成为核心的在线虚拟旅行体验产品。

因此，当前最合理的落地方式是：

- 以 Web First 作为首发容器
- 使用 React + PixiJS 构建互动场景
- 使用配置驱动承载地图、景点、Action 与 Event
- 使用服务端管理内容、用户状态与 AI 任务
- 先做出一个可闭环、可试玩、可扩展的 MVP

这份文档即作为后续 Agent、前后端、产品和设计协作的基础版本说明书。
