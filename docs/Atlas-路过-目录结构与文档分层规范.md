# Atlas - 路过 目录结构与文档分层规范

> 目的：明确仓库中不同目录的职责边界，避免“稳定文档 / 滚动规划 / 执行任务 / 角色定义”混在一起。
> 本规范属于稳定的仓库组织约定，因此放在 `docs/`。

---

## 1. 设计原则

仓库中的文档与目录按职责分层：

1. **稳定规范层**
   - 长期成立、用于理解系统与协作方式
2. **滚动规划层**
   - 会持续迭代的内容规划、扩展路线、资料池
3. **执行任务层**
   - 面向具体角色的任务拆分与验收
4. **角色边界层**
   - 定义 worker 的职责、可改范围、输入输出

---

## 2. 目录职责

### 2.1 `docs/`
用于承载稳定文档，包括但不限于：
- MVP 技术方案
- 数据模型设计
- API 协议说明
- 协作规范
- 前后端开发规范
- 系统设计稿（如 NPC 对话设计、LLM 路由设计）
- 仓库结构与分层规范

`docs/` 中的文档应尽量满足：
- 不随短期排期频繁波动
- 作为系统级共识长期存在
- 可被多个任务与角色长期引用

### 2.2 `planning/`
用于承载滚动规划文档，包括但不限于：
- 景点与地图扩展规划
- 城市扩展路线图
- 素材补充总表
- 逐景点资料卡
- 逐区域 / 城市资料卡

`planning/` 中的文档通常具有：
- 阶段性
- 优先级
- 候选池
- 待确认项
- 会被不断补充和修订

### 2.3 `tasks/`
用于承载具体执行任务：
- 谁来做
- 改哪些文件
- 验收标准
- 勾选状态

任务文件必须自包含上下文，能被独立 worker 直接拿去执行。

### 2.4 `workers/`
用于承载角色定义：
- 角色职责
- 可改范围
- 默认禁止触碰的目录
- 典型输入输出
- 与其他角色的协作方式

它回答的是“这个角色一般负责什么”，而不是“本次要做什么”。

---

## 3. 典型用法

### 新能力的正常流转

```text
docs/         先定义系统边界、协议、设计
planning/     再补内容规划、资料池、扩展路线
tasks/        然后拆成本次可执行任务
workers/      由角色说明来约束谁来做、谁不能越界
```

### 例子
- “LLM 多 Provider 路由设计” → `docs/`
- “景点与地图扩展规划” → `planning/`
- “08-LLM多Provider-后端.md” → `tasks/`
- “05-景点和地图策划.md” → `workers/`

---

## 4. 落地规则

### 4.1 什么应该放到 `docs/`
- 长期有效的规范、协议、设计
- 不依赖单次排期的架构文档
- 面向全局的系统性说明

### 4.2 什么不应该继续堆在 `docs/`
- 某阶段的城市候选池
- 滚动变化的景点优先级
- 策划排期
- 逐景点故事资料卡

这些内容应迁到 `planning/`。

### 4.3 什么应该放到 `planning/`
- 现有内容补充计划
- 新城市 / 新景点候选池
- 素材与故事补充路线
- 逐景点 / 逐区域资料卡

### 4.4 `planning/` 不是事实真相源
- 最终数据真相仍在 `shared/src/seed/dataset.ts`
- 最终契约真相仍在 `@atlas/shared`
- 最终接口真相仍在 `docs/Atlas-路过-API协议说明.md`

`planning/` 提供的是**结构化输入与优先级建议**，不是实现真相。

---

## 5. 目录协作原则

- 架构师负责判断文档应该进入哪一层
- 景点和地图策划角色主要产出到 `planning/`
- 任务执行角色主要消费 `planning/`，并把执行细节落到 `tasks/`
- 若某份规划已经沉淀成稳定共识，可再上升到 `docs/`

---

## 6. 一句话总则

**`docs/` 放稳定共识，`planning/` 放滚动规划，`tasks/` 放执行任务，`workers/` 放角色边界。**
