# Atlas - 路过 Agent 执行入口

## 1. 文档目的

本文档作为“路过（Atlas）”项目的 Agent 开发执行入口，定义文档阅读顺序、开发阶段、Agent 分工、执行约束与交付要求。目标是让多个 Agent 或研发成员能够基于统一上下文并行推进，避免重复设计、接口漂移和实现分叉。

---

## 2. 项目基础信息

- 中文产品名：**路过**
- 项目代号：**Atlas**
- 项目定位：在线互动式虚拟旅行体验产品
- 当前目标：完成可闭环、可试玩、可演进的 MVP 版本

MVP 核心体验：

1. 用户从世界地图进入区域
2. 用户进入景点并执行轻交互 Action
3. 系统返回 Event / Reward / AI 结果
4. 用户形成收藏、记录与分享结果

## 5. Agent 分工建议

建议至少拆成 4 类 Agent。

### 5.1 Agent A：前端基础骨架
职责：
- 搭建 Next.js / TypeScript 工程
- 搭建路由、状态管理、请求层
- 搭建图鉴、分享、基础页面

输入：
- MVP 技术方案
- 前端技术设计
- API 协议说明

输出：
- 可运行的前端基础工程
- 页面骨架
- 全局状态骨架

### 5.2 Agent B：场景与动画
职责：
- 搭建 PixiJS 场景层
- 实现 World / Region / Spot 场景结构
- 实现相机与转场逻辑
- 实现 Action 面板与 Event Layer 展示

输入：
- 前端技术设计
- 数据模型设计
- API 协议说明

输出：
- 可运行的互动地图层级
- 场景切换效果
- Action / Event 基础交互

### 5.3 Agent C：后端内容与行为
职责：
- 建立后端服务框架
- 建立内容配置读取能力
- 建立 Action / Event / Progress / Reward 逻辑
- 提供联调接口

输入：
- MVP 技术方案
- 后端技术设计
- 数据模型设计
- API 协议说明

输出：
- world / region / spot 查询接口
- check-in / execute-action 接口
- 用户进度与奖励逻辑

### 5.4 Agent D：AI 链路
职责：
- 建立上传接口
- 建立 AI task 创建与状态查询
- 建立生成结果回写逻辑
- 对接前端图片生成链路

输入：
- 后端技术设计
- API 协议说明
- 数据模型设计

输出：
- 上传能力
- 任务系统
- 结果查询接口

## 6. 开发阶段建议

建议按 4 个阶段推进。

### 6.1 阶段一：基础骨架
目标：跑通工程结构与基础页面

前端：
- 初始化工程
- 建立路由
- 建立 store
- 建立 mock 服务

后端：
- 初始化服务
- 建立数据库连接
- 建立基础模块
- 建立 mock 数据与配置接口

验收标准：
- 前后端均可本地运行
- 可通过 mock 数据展示 world / region / spot 基础信息

### 6.2 阶段二：地图与 Action 闭环
目标：跑通从地图进入景点并执行动作

前端：
- World / Region / Spot 场景跑通
- Action 面板可交互
- EventModal / RewardPopup 可展示

后端：
- `GET /api/world`
- `GET /api/regions/{id}`
- `GET /api/spots/{id}`
- `POST /api/spots/{id}/check-in`
- `POST /api/actions/{id}/execute`

验收标准：
- 用户可以从 world 进入 spot
- 至少一个 Action 能返回 Event 与 Reward

### 6.3 阶段三：AI 图片链路
目标：跑通上传、任务与结果展示

前端：
- 图片上传 UI
- 任务轮询
- 结果页展示

后端：
- 上传接口
- task 创建接口
- task 查询接口
- result 查询接口

验收标准：
- 用户可以上传图片并看到生成结果或模拟结果

### 6.4 阶段四：资产与联调收口
目标：形成 MVP 可试玩版

前端：
- 图鉴页
- 生成记录页
- 分享页

后端：
- collections 接口
- generated-assets 接口
- achievements 接口（可简版）

验收标准：
- 从地图探索到结果沉淀形成闭环
- 前后端主协议稳定

## 7. 执行约束

所有 Agent 必须遵守以下约束：

### 7.1 架构约束
- 不要把景点逻辑写死在页面组件中
- 不要把事件逻辑散落在 UI 层
- 地图层级切换统一由 Scene / Camera 机制管理
- 所有内容实体必须保留配置入口

### 7.2 接口约束
- 优先遵守 `Atlas-路过-API协议说明.md`
- 接口变更前必须先更新协议文档
- Action execute 返回结构优先稳定，不随意变更

### 7.3 数据约束
- 优先遵守 `Atlas-路过-数据模型设计.md`
- 不新增与现有结构冲突的关键字段
- 用户状态和配置实体必须分离

### 7.4 体验约束
- 不要用页面跳转替代地图分层体验
- 不要用复杂玩法拖慢 MVP 进度
- 优先保证主闭环可用，再做视觉细节优化

## 11. 最小验收标准

Agent 开发完成后，必须至少满足以下标准：

1. 用户可进入世界地图
2. 用户可从 Region 进入 Spot
3. 用户可在 Spot 中执行至少 2 类 Action
4. 系统可返回 Event / Reward 结果
5. 用户可完成至少 1 次图片上传与生成任务
6. 用户可在记录或图鉴页看到结果沉淀

---

## 12. 建议执行顺序

推荐按以下顺序启动开发：

1. 读取 `Atlas-路过-MVP-技术方案.md`
2. 建立前后端工程骨架
3. 固化数据模型与 API 协议
4. 跑通 World → Region → Spot 主链路
5. 跑通 Action → Event → Reward 主链路
6. 跑通 AI 上传 → Task → Result 主链路
7. 补齐图鉴 / 记录 / 分享
8. 联调收口并准备迭代

---

## 13. 结论

本文件用于统一 Agent 执行入口，确保所有开发行为围绕同一套规划推进。执行过程中，如出现实现分歧，应优先回到总纲文档、数据模型文档和 API 协议文档进行对齐，而不是各自演化。
